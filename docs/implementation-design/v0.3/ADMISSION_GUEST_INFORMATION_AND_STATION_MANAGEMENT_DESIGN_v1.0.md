## 1. Executive objective and product boundaries

Deliver an integrated arrival-to-destination experience for Eventor-managed events. An authorized organization configures entrances, reception, guest information desks (Info Pult), seating assistance, print stations and passive information displays. A guest presents an admission pass at an entrance, receives a trustworthy admission result and can subsequently find their own assigned location, programme, facilities and approved notices at an information point or on their own phone. A reception operator can assist without searching the organization's entire Guest Registry. Event managers see authorized station health, arrival counts, allocation exceptions, print status and operational alerts in the Event Operations Cockpit (EOC). The same application and supported devices serve multiple operating modes; each mode has a distinct authorization and data boundary.

The core product rule is **admission is not information access, information access is not attendance, and attendance is not RSVP**. Issuing, printing, presenting, previewing or looking up a credential never itself confirms arrival. Physical attendance is a separately authorized, atomic event/session command. Information screens may read the current approved personal destination but cannot commit allocations or grant admission. Changing a seat never silently cancels admission or replaces credentials. A printed position is a historical snapshot; an authorized live view resolves the current published position.

Support halls, banquets, fixed theatre rows, mosque/prayer rows and floor positions, mixed layouts, standing or count-based zones, multi-building venues, multi-session events and accessible routes. Do not invent seats for standing guests. Provider-only operation requires none of the guest/admission modules. A venue provider does not acquire organizer guest data merely by providing equipment, a venue or an Info Pult. Each enabled capability has an accountable organizer or explicitly delegated operator. GHB is a reference organization, not a product-specific tenant baked into code.

Scope includes secure QR credential lifecycle, scanning, minimal lookup, public and personal projections, station registry, typed station designer, device binding, supervised and optional self-service modes, privacy, print/reissue, live events, bounded degraded operation, audit, diagnostics and acceptance. It excludes biometric identification, facial recognition, continuous indoor positioning, automatic tracking of guest movements, a public guest directory, arbitrary device remote desktop/OS administration, cloud-required kiosk management, autonomous access control of locks/turnstiles, law-enforcement functions and unattended emergency overrides. A scan result assists authorized humans; it is not a guarantee of a physical person's identity or actual entry. Integrations with physical turnstiles, badge NFC, identity-document readers, remote print agents or managed OS kiosk systems require a separate reviewed design if desired. No new microservice, mandatory SaaS or parallel identity/guest/branding/allocation/attendance subsystem is authorized.

## 3. AGIS-01 — Station taxonomy and physical/operational model

Separate **physical place**, **logical station**, **device installation**, **operator/session**, **mode profile**, **event/session assignment** and **authorized capability**. One physical counter may have multiple devices or logical stations; a mobile device may be re-assigned to a different station. No assumption that an IP, browser fingerprint or station name is a trusted identity. A station is a scoped operational endpoint, not a new organization or a staff account. A fixed station has an optional physical venue anchor and localized human label. A roaming station uses an approved starting point or asks the operator to select one; no automatic location tracking.

| Mode | Typical user / equipment | Allowed primary operation | Explicitly not implied |
|---|---|---|---|
| Entrance/gate | Signed-in gate operator, camera tablet/USB scanner | Verify admission, explicit arrival/departure where policy allows, exception escalation, minimal destination | Full roster, general Registry, guest contact, allocation edits, issue/reprint |
| Supervised self-service Info Pult | Registered kiosk device, guest touchscreen + scanner; staff nearby | Minimal verified guest-specific view and public directions/programme, end session | Staff session, attendance recording, arbitrary guest search, write access |
| Staffed Info Pult | Signed-in support operator, desktop/tablet | Exact pass lookup or scoped manual search with verification, guidance and permitted print request | Admission, guest export, editing contacts, seating changes, broad history |
| Seating assistance | Assigned seating operator | Minimal destination lookup; reviewed allocation move via owning #106 command only if separately permitted | Bypass constraints, solver auto-commit, attendance correction |
| Print/issuance assistance | Authorized operator and selected printer/output workflow | Approved document print request, controlled reissue using credential service where granted | Raw token reveal, uncontrolled credential generation, arbitrary printer commands |
| Passive information display | Restricted read-only device/browser | Approved welcome, programme, public directions, notices, safe zone legend | Personal lookup, personal markers/guest names by default, any domain mutation |

Each mode has purpose allowlist, identity type, required capabilities, scope, allowed fields/actions, layouts, failure behavior and audit requirements. A station may have permitted modes but only one active operational mode per device binding at a time. Use deliberate, authorized transition: end existing guest view/operation, flush or quarantine unresolved local work, verify new actor/context/assignment, revoke old station lease, load new safe layout. Shared devices cannot carry staff credentials into guest mode. A supervisor must be able to tell which mode is active by text and icon, not color alone. Gate and Info Pult have different scan commands and confirmation semantics; never a single generic endpoint with a client-supplied `recordAttendance=true` switch that grants authority. A passive display cannot become a scanner by editing a URL.

### Reference journey (synthetic)

GHB OAC administrator defines Entrance A, Entrance B, Info Pult Foyer, Info Pult Assisted, Seating Help Hall, Print Desk and Welcome Display; assigns them to a fictional event and approved map anchors. Event manager opens EOC → Stations, confirms event/session windows, tests hardware, chooses published layouts, links authorized operators, reviews readiness and activates. Guest shows a printed admission pass at Entrance A; the gate result records arrival exactly once. At Info Pult Foyer, the guest scans the pass, completes configured minimal verification, sees their current destination and route, changes language, and presses Finish. The kiosk clears personal content and returns to neutral start. If the guest has a dedicated portal link, they can instead use their own phone. Assisted staff resolve missing allocation or wrong building via minimal support lookup and request an authorized change; after approved publication, new lookups reflect the new seat. Welcome Display shows only public programme, signs and notices. Organizer closes the session/event; station bindings expire/close, unresolved scan and print queues reconcile and authorized reports remain. No platform owner action is required for routine station setup or operation.

## 4. AGIS-02 — Tenant self-service, event activation and readiness

OAC → Administration → Station profiles and devices: tenant-owned reusable mode presets, screen layouts, permitted hardware inventory, default locale, accessibility preferences, printer profiles and venue anchors. Venue configuration under #105 owns the physical anchor and guest-visible projection; event selection under #104 owns event/session and capability policy. EOC → Stations: instantiate/assign station for a selected event/session, choose authorized profile/revision, configure permitted modes, station code, label, physical origin, start/end window, operator/station grants, devices, output and degradation policy. No platform owner needed, subject to PAC permitted limits and OAC delegation ceilings. Tenant profile defaults are not hard restrictions; event overrides must be validated and scoped. Partner operator may receive a narrow task/station grant from organizer; no use of a booking-only linking grant as scanner permission.

Activation checklist must be computed from current server state, not stored checkboxes. Per mode show required/optional/not applicable, cause and remediation; separate admission readiness from information readiness, print readiness and passive display readiness. Admission requires active event/session, allowed credential/admission policy, authorized station and operator, reachable server or explicitly approved degraded policy. Seating map requires current guest-safe publication and applicable assignment; textual destination or human help if absent. Info Pult requires valid configured verification and secure device/session, approved public projection, privacy reset. Print requires approved purpose/template, verified printer/media path or authorized download alternative. Display needs public-only published content and device authorization; no guest modules required for a generic programme display. No SMTP prerequisite for local gate scans or offline-independent workflows; if using one-time email verification the corresponding channel must be configured or a staffed fallback selected. Unavailable dependencies are visible; unsupported mode cannot be activated. Draft configuration can be saved before all dependencies are ready. Activation does not issue credentials, send emails or publish unrelated content.

Lifecycle: logical station draft → ready/active → suspended/disabled → reactivated or retired. Map to existing status values where possible; distinguish configuration draft, operational readiness and active runtime state rather than overloading existing `status`. Station or event changes require expected revision, review impacted live leases and unresolved queues, actual actor and reason for consequential change. Disable/revoke blocks new authorized operations at server immediately; UI lock on next successful contact or local expiry, not a promise to physically control disconnected hardware. Retire preserves codes/history, no destructive removal while referenced. Reopen requires explicit current grant and readiness. Event closure/cancellation, membership suspension, module disable or device revoke invalidates dependent scopes; no mass attendance changes or cancellation side effects from station state. Retain explicit exception review for unsettled offline attempts and print outcomes. Copying event/station templates copies configuration references only; never live tokens, device leases, guest sessions, queue or attendance history.

## 5. AGIS-03 — Configurable Station Designer

Deliver a visual, accessible, constrained **Station Designer** (not arbitrary HTML/code or a general web page builder) within the OAC/EOC configuration workflow. It may reuse TDS design primitives, brand library and validated assets, but interactive behavior is a separately typed station layout schema with fixed trusted actions and data projections. A nontechnical administrator selects purpose, layout preset (portrait kiosk, landscape kiosk, gate compact, assisted desktop, scanner mobile, print desk, passive full-screen), edits localized welcome/help and labels, places supported panels and buttons, sets allowed theme tokens, safe sizes, ordering, reading/focus order, idle/timeout behavior within policy bounds and device form factor. Provide visual drag/drop and keyboard move/reorder controls, undo/redo, grid/snap, preview on supported sizes and validation before publish. Templates permit reuse within tenant and explicit platform-default distribution; no cross-tenant private assets by reference without authorization.

| Component type | Purpose binding and rules |
|---|---|
| Brand/header, welcome, text/illustration | Approved shared brand/asset revision, localized bounded text; no arbitrary remote embeds or script. |
| Scan prompt / input | Purpose-specific decoder/input component; fixed allowed action enum; cannot submit credentials to a custom URL. |
| Admission result | Gate-only safe result, large status words/icons and bounded destination; cannot hide material denied/duplicate/pending/stale state. |
| Guest identity / location card | Authorized minimal guest projection only; self-service verified session required; configurable field subset, no custom query. |
| Map/wayfinding | Sanitized published guest projection or permitted staff map; own marker only for personal views; route anchor and textual fallback. |
| Programme / announcements / venue info | Published audience-filtered data; public display variant strips all personal data. |
| Language, accessibility, help, finish | Fixed safe controls; never remove Finish/timeout indicator where applicable, essential errors or accessible navigation. |
| Print request / assistance action | Only where mode and actual grants allow; reviewed document purpose, no raw printer command or issue authority. |
| Station health banner | Server-reported or local connectivity/readiness, truthful timestamp and stale state; public view uses nonsensitive message. |

Typed schema example (illustrative, not runtime JSON contract): `{"schemaVersion":1,"mode":"info_self_service","orientation":"portrait","components":[{"id":"header","type":"brand_header"},{"id":"scan","type":"credential_scan","purpose":"info_lookup"},{"id":"seat","type":"destination_card","binding":"guest.approved_destination","when":"verified_personal_view"},{"id":"map","type":"guest_map","binding":"guest.safe_route"},{"id":"done","type":"finish_session"}]}`. Validate at draft save and server publication: schema version, component count/size/depth, unique IDs, placement/no overlapping essential controls, compatible mode/binding/action, mandatory safety/status components, verified locale variants, contrast, keyboard order, assets, timeouts and policy caps. No arbitrary expressions, SQL, template loops on roster, raw JS/CSS/HTML, network calls, user-provided URL targets, iframes, third-party trackers or dynamic plugin execution. Server chooses projection; hiding a field in a layout never authorizes it. Safe built-in fallback layout if revision missing/incompatible; do not silently downgrade security checks or run an unreviewed layout. Show blocked mode if no safe fallback.

Lifecycle: draft → preview (synthetic data, explicit TEST label, fake QR non-live) → reviewed published revision → assigned to station → active at session boundary or reviewed live switch → superseded/retired. Store immutable revision and digest; publish does not activate every station. Active lease pins exact layout and brand/asset resolution revision; authorized rollout can switch atomically, with update notice and reload after current personal session/scan finishes or clear/lock immediately for security fixes. No changing historical artifacts or audit by editing a preset. Rollback means publish/select prior validated revision under current policy, not undoing attendance. Stale draft and review rejected. Test all modes with compact/default layouts first; advanced composition delivered when scheduled with #111/UX, not prerequisite for core gate flow. Provide examples with fictitious labels (GHB — Ulaz A, Info Pult, Svečani prijem), no actual logo or private venue plan assumed.

## 6. AGIS-04 — Authorization, actor types and station capability resolution

Use existing staff session and membership/scope model. Tenant role grant alone does not prove assignment to a station; station binding alone does not grant a staff role. Effective authorization for an interactive staff command = deployment/tenant/event capability enabled and lifecycle valid ∩ authenticated active membership ∩ exact domain permission and allowed event/session/station/task scope ∩ current station assignment and device/lease ∩ mode/action allowlist ∩ current policy/verification requirements. For guest kiosk: registered restricted device + correct station/session + separate short-lived verified guest information session + allowlisted fields; no staff permissions. For public display: restricted display principal or genuinely public published audience projection (explicit policy), no personal credential or guest lookup. For print workers: narrow service identity consuming authorized jobs and rechecking eligibility; never fake a human actor. Platform support uses PAC controlled scoped access and actual actor, not implicit broad guest privilege. Preserve ADR 0015 while successor authority review is pending.

| Role / actor | Proposed authority (permission bundles, not hardcoded roles) |
|---|---|
| Organization owner/admin | Configure tenant profiles/devices/approved brand/settings; delegate within ceiling; no implied sensitive roster/override access. |
| Event administrator / station supervisor | Manage assigned event stations, activate/disable/assign, view health and operational summaries; high-impact correction/reissue separately authorized. |
| Gate operator | Exact station/session scan and bounded manual lookup; manual arrival if explicitly granted; no unrestricted Registry access. |
| Reception / guest support operator | Scoped guest information lookup and guidance, minimal fields; print request only if granted. |
| Seating coordinator | Assigned allocation/zone actions under #106 and publication rules; no blanket admission permission. |
| Credential issuer / print operator | Distinct issue/revoke/reissue and print/download permissions; no implied guest export or attendance mutation. |
| Device / kiosk | Bound mode endpoints only; no staff login, guest directory or broad device control. |
| Guest | Own verified personal event view; no arbitrary reference lookup. |
| Display | Read-only approved public projection; no personal session. |
| Auditor / manager | Authorized filtered audit/report/health projections; not raw credential or contact access. |
| External contracted operator | Explicit grantor-approved task/station action and field projection plus grantee membership; no general provider access. |

Proposed permission families (align existing catalogue during M0, not preapproved codes): `station.read/manage/activate/disable`, `station.device.enroll/revoke`, `station.layout.design/publish`, `station.operate.gate/info/seating/print/display`, `admission.issue/revoke/reissue/scan/manual/correct`, `guest.info.lookup`, `guest.info.verify`, `allocation.change/publish` (reuse existing equivalent), `station.print.request/retry/reissue`, `station.health.read`, `station.audit.read`. Separate ordinary read/operate from issue/revoke, layout publish, attendance correction, delegation, export. Unknown/new permissions default deny. No grant ceiling based solely on role name. Sensitive actions require current reason, recent auth/step-up or second approval per policy and PAC; normal scan should not require MFA each guest but initial operator auth and expiring lease must be strong. A non-guest device principal cannot use generic staff APIs. Cross-tenant collaboration requires explicit action and projection; ADR 0023 exact linking-only grant cannot authorize these functions. Every API query, command, job, export/download and stream revalidates effective scope; UI navigation is not permission. Use server time and explicit current organization/event/session; no cross-tenant references accepted from client body.

## 7. AGIS-05 — Admission credentials and QR format

Issue credentials via a dedicated admission domain command only after authorized selection of participation, event and policy; no issuance on invitation/RSVP, preview, rendering, lookup or publication. Use a CSPRNG opaque purpose-specific value (proposed at least 128 bits entropy, preferably 256; version/purpose prefix optional), no name, seat, category, phone, email or meaningful guest ID encoded. Existing `admission_credentials.token_sha256` stores digest only; use canonical byte/string encoding and strict bounded parser, no arbitrary URL opening, no token in query string/access logs/analytics, response headers, audit or browser history. A credential is bound to organization, event, participation and eligibility policy. Session access is an explicit permitted scope derived from policy, not every session automatically. Event-level pass may cover several sessions; per-session restrictions require reviewed scope representation. Do not weaken existing one-active-per-participation index simply to support multiple kinds; M0 review purpose/eligibility and existing `staff_badge`/`other` handling, preserve prior credentials. Staff access badges do not authenticate a staff session or imply guest attendance.

Credential lifecycle: issue → active within validity window → revoked or expired. Check expiry in the authorization transaction using server time even if status maintenance job has not marked expired; never resurrect by restoring old artifact. Revoke with reason, actor, current revision and audit; no attendance deletion. Replacement locks participation/credential, verifies current permission, atomically revokes prior active pass and issues replacement, writes linked history/receipt; failed render/print does not reactivate old pass or create multiple active credentials. Retry of issuance with same request id returns existing result metadata, not a fresh token; changed payload conflicts. Use safe recovery if raw output unavailable. Raw live credential material only in immediate restricted issuance response or existing reviewed encrypted short-lived delivery/print artifact boundary; never reconstruct from hash, never store plaintext in ordinary DB fields. If an artifact is retained, enforce encryption, private object access, current validity and download auth, expiry and deletion policy. Purpose-specific invitation and portal link tokens remain independent. No credential exposure in TDS synthetic previews or sample data. Include human-readable nonsecret event reference and approved fallback/help text; reference alone is not an access credential.

QR physical design in TDS uses typed `admission.qr` binding from authorized domain projection; preserve quiet zone, contrast, module shape, error-correction choice validated at physical size, no decorative overlap or arbitrary resizing; decode final PDF/render and actual printed samples. Suggested print-size/contrast settings require tests on target devices, not a universal minimum claim. QR decoder returns a bounded string, never executes URLs or links; accept only explicitly versioned admission/portal payload forms and the expected purpose. Wrong-purpose, unknown, forged, revoked, expired, wrong-event, ineligible and not-yet-valid passes fail without exposing whether a person belongs to another event. No automatic conversion to a portal credential; a guest presenting an admission pass at information station follows separate verified lookup below.

## 8. AGIS-06 — Gate scanning and attendance state machine

Gate UI has large current organization/event/session/station label, operator identity, station mode, connectivity, camera/manual/HID scan choice, neutral ready state, large outcome and optional safe destination. On accepted scan show success word/icon, server-confirmed arrival time, current destination if permitted; duplicate shows already recorded and permitted first-arrival details, not another success record; rejected/invalid shows safe reason and assistance path; offline queue shows pending, never green accepted. Use optional accessible audio/vibration configurable per station, not sole signal. Reset scan result after bounded dwell or explicit next guest; clear personal state on lock/leave. Prevent repeated frames from spamming requests by debounce and in-flight guard; server remains authoritative. Camera permission denied/no camera/unreadable pass → manual scoped lookup and authorized arrival path. Do not open external URLs from decoded QR. For fast operations a single deliberate physical scan in armed gate mode may be the explicit arrival command **only when event policy permits scan-to-confirm**. Where Blueprint §13.2/event policy requires operator confirmation or identity verification, first obtain a non-mutating, short-lived reviewed validation receipt and show the safe result; then explicitly confirm arrival with the receipt and recheck all current authority, credential, eligibility and state under lock. Validation alone never records attendance; a receipt is not an admission grant. Camera preview or test mode performs no command. For manual/exception/reentry/correction require reviewed explicit action as policy. Never infer arrival just from an info lookup or portal visit.

### Transactional scan contract

1. Authenticate current operator and restricted station lease, validate capability, lifecycle, device/assignment and scope. Normalize bounded input and idempotency key; no untrusted actor, station or organization claim accepted as authority. Lock authorization/lifecycle rows in documented canonical order consistent with existing revocation/cancellation patterns. Recheck current effective authority under lock; use RLS/scoped routines. Unauthorized requests produce safe denial and appropriate security audit, never fabricated membership scan record.
2. Resolve digest in exact authorized event; validate credential kind/status/time, current participant eligibility and session policy; wrong/unknown gets safe error. Lock participant/session admission subject and credential in canonical order with reissue/revoke/attendance correction. Handle no allocation separately; admission may be allowed without a seat under policy, or escalated if seating required. Do not use RSVP yes alone as eligibility and do not change RSVP.
3. Enforce unique effective arrival according to explicit policy. Default one initial arrival per participation/session. Use DB serialized subject/current-state guard or equivalent uniqueness constraint and canonical locked command; existing attendance history alone is insufficient evidence of race safety. If already present, duplicate attempt; departure/re-entry only where policy explicitly enabled (separate actions and visit sequence or equivalent invariant). One attendance fact per permitted transition, append-only records, preserve original times. No client clock as authority. At two concurrent gates for same valid pass, exactly one initial arrival accepted, other duplicate; both attempts attributable. Duplicate attempts never increment current present count.
4. Write attempt, successful attendance transition if any, audit and outbox atomically. No accepted UI if transaction aborts. Current attendance projection is derived/reconciled from authoritative append-only actions and subject lock; corrections append reason and target, never overwrite. Add integrity check for attempt/session/station/participation association where needed. Safe outcome includes receipt id, server time, disposition, only authorized minimal destination with revision/as-of. No raw token or other guest info. Commit before response.
5. Idempotent retry of exact same intent under same station/actor/key returns original command receipt without new attendance; changed payload/key binding conflicts. Revalidate current auth and redact/reject stale personal projection on revoke/expiry; original accepted fact remains historical, retry cannot imply a current pass or seat. Lost response shows unknown/pending and retry/receipt check, not repeated independent scan or local success. Separate request key from physical duplicate detection; repeated scans with new keys are duplicate attempts, not duplicate attendance. Use bounded rate limit per station/device/operator and safe invalid-attempt fingerprint for abuse diagnostics.

| Condition | Outcome and state effect |
|---|---|
| Valid pass, eligible, new arrival | accepted; one append-only arrival and effective present transition |
| Same subject already present/arrived under one-entry policy | duplicate; no attendance change |
| Unknown/malformed/wrong-purpose/wrong-event/expired/revoked | invalid or rejected (safe display); no attendance |
| Not eligible, outside window, unassigned required destination | rejected or assistance; no silent eligibility change |
| Event/session cancelled or capability disabled | explicit safe denial; no new attendance |
| Operator/station/device revoked or context wrong | unauthorized/locked; no domain mutation; security audit |
| Network/response uncertain | queued/pending or unknown receipt; not accepted until server resolves |
| Manual authorized arrival/correction | distinct command, verified subject/reason/authority; append history |

Attendance semantics must distinguish ever arrived, currently present, departed, corrected and manual entry; event/session counts explicitly labeled. Multi-session attendance is not duplicate across different authorized session subjects. Event-level total distinct people vs sum of session arrivals must be clear. Do not infer guest movement from info scans; no background location telemetry. Default no reentry/departure action unless policy explicitly enables it and current UI states action. Emergency egress must not rely on Eventor; safety procedures are external and no software denial should be represented as physical enforcement.

## 9. AGIS-07 — Manual lookup, assistance and attendance correction

Support exact event reference/pass, bounded name search in assigned event/session/station scope and disambiguation with only authorized minimal fields (e.g. recorded event display name, nonsecret reference, destination); not global Registry search. Default no phone/email, private categories, internal tags, restricted notes, full relationship/participation history or other events. If permitted exception admits an otherwise blocked guest, distinguish supervisor authorization and reason from ordinary scan; no override of tenant/event/capability/integrity/security denial. ## 10. AGIS-08 — Self-service Info Pult and purpose-limited verification

A supervised venue kiosk is not simply a logged-in staff browser left open. It is a dedicated restricted device principal and station context with a neutral start screen, public event information and scan prompt, purpose-limited lookup, configured verification, personal view, Finish/timeout and complete reset. Default deployment mode supervised; optional unattended configuration is a policy choice with explicit risk assessment and privacy settings. Do not display guest name/seat solely from admission-pass presence unless policy and review establish that as sufficient for a narrowly bounded staff-assisted projection; for self-service require separate minimal verification as Blueprint §34.2 specifies. Possession of a pass is not general profile access. Higher-risk events may require verified contact one-time code, dedicated portal credential, supervised identity confirmation or other reviewed independent factor. A printed nonsecret reference or publicly visible name is not an independent secret. Do not require an email channel or guest account for every event; use staffed assistance fallback when independent verification is unavailable. Never reveal masked contact data unless permitted and necessary; send challenges only to preverified channel with rate limits and neutral response. Do not solicit identity documents or biometric data by default.

Flow:

- Guest selects bs-BA/en or configured language and scans QR. Device sends bounded payload to dedicated **information** endpoint using registered station lease. Server checks station, event, session, purpose, current credential validity and policy; does not insert check-in attempt/attendance or alter RSVP/eligibility. Audit is a separate information access event, not an arrival. Unknown/revoked/wrong scope uses neutral error; no roster enumeration. If guest supplies dedicated portal QR, use separate verification flow, do not convert admission pass into portal link. Scanner input never navigates to decoded URL.
- Server starts short-lived challenge scoped to tenant/event/participation/device/mode, opaque nonce bound to purpose and attempt limit. Return only generic next step; no personal fields before verified. Complete independent verification or authorized staff-assisted confirmation through staff identity; no shared admin password, no guest selection from raw roster. Challenge is single use or tightly bounded retry, expiry and revocation checked. Server creates limited kiosk view session, purpose-specific and nontransferable, short absolute/idle expiry, no staff privileges or general portal access. No raw long-lived admission pass retained in browser after resolution. Guest does not get general profile token from kiosk; sending/handing off to phone requires separate approved portal issuance/verification path, no public URL containing raw admission credential.
- Personal result uses one current approved participation projection and authorized session context. Allow displayed recorded event name only if policy, own destination, current published revision and update/as-of, venue directions, programme, approved facilities and notices, language/accessibility/help. No other people/positions marked by identity, private occupancy/guest list, contacts, security layers, reasons for seat assignment, private RSVP history or sensitive group tags. If accompanying guest view is explicitly enabled use separately authorized relationship and projection per Blueprint, default off; shared pass does not imply group access. No ability to edit person, RSVP, assignment or attendance on kiosk. Print simple directions if enabled and safe (see AGIS-12); credential reissue requires staff approval. Public programme usable without personal lookup if published audience allows.
- Finish, timeout, new scan, lock, operator handover, browser back/reload, crash/restart, expiry, device revoke and event closure clear personal view/session and any pending challenge. Guest session cannot be rehydrated from URL, persisted local state or history; use no-store response headers and service-worker deny-cache list, clear memory, abort outstanding requests, reject late responses with generation/context guard. Clear form/QR, canvas map marker, print preview, accessibility live-region announcement and clipboard as controllable; never copy tokens. Do not promise app can erase screenshots, browser/OS crash dumps or physical printouts; managed kiosk OS policy, privacy screen, no unattended private display, safe placement and operator training are complementary. Local inactivity timer enforces screen reset even if disconnected. No personal state in back-forward cache (reset on pagehide/pageshow, test target browsers); require server lease check before reopening. Device returns to public neutral screen, or locked/degraded screen if lease invalid. Record session start/outcome/end/timeout audit with minimal IDs and no raw data; short retention, avoid tracking paths between stations.

Candidate policy defaults for review: challenge 2 minutes, max 5 attempts per challenge plus station/subject/global abuse limits, personal idle 30 seconds with visible countdown/Finish, absolute 90 seconds, no indefinite extension; accessible extension within bounded maximum and re-verification if expired. Policy may shorten for higher-risk events. Do not treat these as already approved production settings. Supervised operator can assist guests with no phone without weakening authorization. If service unavailable, public approved static instructions only; no stale private destination or public personal lookup. Private session cleared immediately on context loss and no indefinite cached guest profile.

## 14. AGIS-12 — Printing, document handoff and controlled reissue

Support guest admission pass, personalized badge, seating card, directional slip, public wayfinding sheet and signage through TDS purpose-specific templates and approved data projections. Separate credential issue, document render, print submission, actual physical output and handoff: a successful PDF generation is not proof of printing or guest receipt. Use existing TDS document render job/manifest proposal; no second arbitrary PDF engine or spooler service by default. Reuse exact template/brand/locale/assets/revision and approved allocation inputs, private bounded artifact storage and authorized downloads. Render preview is synthetic with TEST watermark/non-live QR. Staff can print an approved valid existing artifact within policy, request current personalized directions, or request authorized replacement. Default Info Pult allows noncredential directions only, with minimal identity omitted when unnecessary; a kiosk must not offer uncontrolled pass issuance or expose a downloadable reusable admission token. Optional self-service direction printing requires verified session, explicit guest request, station printer selection fixed by admin, quotas, minimized output, auto-clear and supervised physical collection if required; no raw PDFs left in guest session. Print fallback is text/on-phone or staffed help. Printing never marks arrived, changes seat or sends email.

Three distinct commands:

| Action | Semantics and controls |
|---|---|
| Reprint approved artifact | Current authorization, purpose, exact prior artifact digest and pass validity, copy limit and reason as needed; no new credential. May produce duplicate physical copies of one pass; gate duplicate guard unchanged. Historical artifacts not presented as current if stale. |
| Render refreshed directions/card | Re-resolve current published plan and approved template with review; credential component only if securely available and valid. No issuance by render, and no attempt to reconstruct token from digest. If raw material is unavailable, route to separately authorized reissue. |
| Replace lost/compromised pass | Explicit verified subject, reason, existing active pass revocation + new issue atomically; review reissue impact, recent auth/approval where required. Old pass rejected even if prior print exists. Print/render failure does not undo credential replacement. Attendance unchanged. |

Print intent records actor/device/station/purpose, participation only where required, artifact/revision, printer profile, media size/orientation/copies, request key/digest, state, server times, validity and result/reason. State machine requested → rendering → ready → authorized handoff/submitted → acknowledged/printed-confirmed where evidence exists; cancelled, failed and uncertain separate. Browser print dialog or opened PDF can only establish handoff/request; it cannot guarantee actual printing. Distinguish user-reported physical completion vs authenticated spool acknowledgement. Timeout after submit or browser crash is uncertain, never auto-reprint credential-bearing artifacts. Operator checks printer output/queue and explicitly reconciles or retries under current authorization; idempotency prevents duplicate server jobs but cannot alone guarantee one physical sheet. Local printer spool, browser downloads and discarded paper can retain PII; document approved cleanup, printer location, quotas, minimum retention, no public network printer credential in client. Printer jam, media mismatch, offline, out of paper, partial batch and stale seating revision need explicit status and safe recovery; split batch by authorized manifest/item outcomes, do not automatically regenerate passes. Direction slips may be noncredential ephemeral documents; only retain minimal job/audit metadata when policy permits. Render worker isolation/no broad network access as TDS; no arbitrary PDF/SVG sources, raw printer command, shell or arbitrary filesystem target. A future local print bridge must use fixed allowlisted printer IDs, signed/authorized bounded job pull, device identity, TLS, short lease, constrained local OS account, no network scanning, no arbitrary remote code. Separate ADR, packaging and threat model before enabling unattended/silent printing. Standard browser print dialog and secure PDF are baseline; silent printing is not promised by PWA alone.

## 16. AGIS-14 — Device enrollment, assignment, operation and revocation

Organization device inventory has nonsecret label, allowed modes, owner organization, optional device class, verification status, last contact/version and revocation; no invasive hardware fingerprint, MAC tracking or IP-based identity. Logical station separate from device; a device binding has event/session/station/mode, allowed actions, assignment revision, approved time window, security-policy revision and server-expiring lease. Default one active binding per device and no concurrent staff/guest mode; multiple authorized devices may be attached to one station only if explicitly allowed by policy, with independent receipt identities. Use dedicated device principal (narrow access), never shared staff credentials. Operator must sign in with own membership for human commands; kiosk/display uses restricted device identity. Device registration grants no staff authority and operator session grants no device enrollment right.

Enrollment flow: authorized admin creates short-lived single-use enrollment challenge bound to intended organization/station/mode or inventory purpose; device displays/accepts pairing code via TLS, admin reviews device label, intended scope and expiry, confirms match; rate-limit failed codes and bind confirmation to authenticated admin/recent auth for high-risk actions. Challenge high entropy where QR/link, short manually entered code requires separate authenticated confirmation and limited attempts; avoid public directory lookup. Device receives narrowly scoped installation credential or key-bound session via reviewed browser/device mechanism, rotates to station lease, stores only essential credential securely per platform constraints. Prefer nonexportable WebCrypto key/secure cookies where feasible, but browser storage/key handles are not hardware attestation; choose in M0/M1 threat review. No long-lived raw staff tokens in browser storage, no shared static kiosk password, no credentials embedded in URL/layout/QR signage. Short lease (candidate 5 min renewable; bound to max station/event window, current assignment, policy and operator session expiry); heartbeat is not authority renewal by itself. Renewal requires valid current binding, device credential, active scope and operator where applicable. Device install credential revocable, rotated and scoped to enrollment/lease, not broad API. Station session cannot extend ordinary staff session expiry or recent authentication. For web-only shared kiosk, managed OS/browser profile and local user controls documented; if secure device enrollment unavailable, supervised session/lock mode only or blocked activation, not weak fallback.

Admin can list device status, assign/reassign, rotate/revoke, lock/unlock logical station via audited command, disable mode, view safe last contact, client build/layout and policy revision, test compatibility. Remote lock is server-side denial plus an instruction to clear on next contact; it cannot remotely lock a powered-off/disconnected OS, wipe disk, stop other applications or guarantee screen erasure. Local timer/lease expiry enforces bounded stale mode. Lock clears data, closes streams, stops scanner camera, denies new commands and invalidates personal sessions; unresolved offline attempts quarantined for authorized review, not deleted silently. Reassign/revoke cannot let previous lease act in new context or replay old queue as new actor. Re-enrollment requires fresh reviewed authorization, old credentials rejected. Station assignment changes preserve audit/history and exact event/session source. Device theft: revoke centrally, rotate affected keys/leases if needed, review queued attempts/print artifacts; no auto-deletion of legitimate attendance. On browser restart require valid lease and new staff authentication if session expired; kiosk neutral screen, no last guest restored. End session/event closes station windows and prevents new operations. PAC global restrictions on unsafe capabilities and health summary, OAC administers own device inventory, EOC controls event assignments; no cross-tenant device enumeration or arbitrary host commands.

## 17. AGIS-15 — Offline and degraded operations contract

Distinguish loss of internet while trusted local Eventor server reachable (normal LAN operation), degraded realtime stream but HTTP commands healthy (refresh/reconnect with timestamp), loss of station-to-server connectivity, server failure/maintenance, and physical device/printer failure. Do not confuse offline web shell cache with offline admission authority. Default **online-authoritative**: no new confirmed admission without successful atomic server response. If request transmitted and response missing, show unknown with receipt/idempotency recovery; never create fresh key automatically. Offline mode optional per event, station and policy; no mandatory offline personal Info Pult lookup. Preserve Blueprint §13.4 bounded offline constraints; if more ambitious mode changes accepted architecture/semantics, approve successor ADR first.

### 17.1 Supported baseline and optional degraded capture

| Mode | Allowed behavior | Prohibited / status |
|---|---|---|
| Online LAN/HTTPS | All authorized configured operations, server validation/transaction | No external cloud dependency for admission. |
| Realtime stream down, API reachable | Poll/refetch scoped snapshot; normal confirmed command responses | Don't label stale metrics live; no duplicate command on stream loss. |
| Disconnected strict mode (default) | Neutral help/public cached safe programme within expiry; local UI shows unavailable; staff follow venue procedures | No new attendance, credential validity or current seat claims; no manual local green acceptance. |
| Bounded deferred capture (opt-in reviewed policy) | Authorized station/operator with preissued bounded offline lease captures pending intents, local dedup, encrypted queue, explicit provisional UI; reconcile when online | No definitive validity/duplicate/revocation guarantee across gates; no personal roster download, reissue, attendance correction, guest info access or allocation edit. |
| Event/server cancellation, device/lease expiry or local clock/queue integrity doubt | Lock new operations; retain encrypted pending queue for permitted reconciliation | No automatic renewal, no circumventing expired or revoked authority. |

Deferred capture is not a guarantee of admission. Event owner may permit human-managed physical admission during network loss based on separately approved local procedures, with clear risk and manual exception review. The system does not retroactively claim a denied/rejected captured scan proves physical entry or silently convert all pending attempts into confirmed attendance. Offline concurrent gates cannot enforce global duplicate prevention or see immediate revocations; never promise both disconnected acceptance and strict real-time uniqueness. If event requires high assurance or immediate revocation, disable offline capture, use staffed fallback/redundant LAN/server. Blueprint §13.4 also explicitly plans a limited encrypted time-bounded **local validation package** for a later PWA mode. Preserve that requirement: the deferred-capture slice is an incremental implementation, not a substitute for local validation. Implement the package extension below after a reviewed threat/consistency decision; do not silently drop it or label capture-only as complete offline validation. Baseline offline queue supports transparent delayed intent only, not local cryptographic entitlement decision. Passive display may cache genuinely public approved content time-bounded; Info Pult personalized content cleared, no guest token/session cache for later reuse. No offline print/reissue involving live credentials.

### 17.2 Queue, lease, privacy and reconciliation

Proposed design: server issues signed or otherwise verifiable offline lease bound to tenant/event/session/station/device/operator (actual membership), allowed capture action, assignment/policy revision, issued/expiry, maximum count and policy window. Do not issue if offline disabled, actor not current or event closed. Local UI shows last server contact, countdown and pending count; use last trusted time plus monotonic elapsed time where available, detect clock reset/restart/rollback; fail closed for new captures if time uncertain. Example pilot bounds: max 10 minutes from last successful authorization, 100 pending intents per station device, max 256 KiB envelope queue (configurable downward, explicit owner policy and tested browser quota); no new captures on exceeded count/byte/window or failed secure persistence. These are candidate caps for review, not established SLA. On tab restart without trusted elapsed time, no new offline work until lease revalidated online. Queue must survive ordinary refresh/crash only if secure persistence is available; otherwise disable offline capture, never imply durable queue stored when write fails. No raw tokens, contact, guest names or seating data in localStorage, plaintext IndexedDB, log, browser history or service worker cache. Encrypt bounded capture payload to server reconciliation public key using reviewed authenticated envelope scheme, binding metadata and unique intent id/counter; server keeps private key protected. Device locally stores ciphertext and minimized metadata only, with nonreversible station/lease-scoped duplicate indicator if needed (key ephemeral; no reusable credential digest directory); purge raw input and temporary bytes promptly. Cryptography design and browser threat model must be reviewed; JS device cannot defend compromised OS or malicious browser extension. Where persistence or secure key handling cannot meet policy, strict mode required. No arbitrary proprietary crypto. Record local observed time as untrusted, counter/order, device/actor lease evidence, station/event/session and capture reason; distinguish server receipt and effective recorded time. Use device authentication/integrity binding and server-verified envelope, don't accept arbitrary actor or forged client timestamps. No admission authorization from a local counter/time alone.

Reconnect: renew/re-authenticate current submitting actor as needed, verify device binding and original lease/actor/capture intent, server decrypts in narrow reconciliation command, validates size, idempotency, original scope, trusted server timestamps, current eligibility/revocation/session policy and conflicts under same atomic attendance lock as online scans. Dedup exact intent by id + canonical fingerprint; different payload conflicts. Do not silently reattribute old actor to new operator. If original operator revoked, old station retired, event closed/cancelled, credential revoked/reissued/expired, time ambiguity, duplicate or conflict: resolve as duplicate/rejected or quarantine for explicit supervisor review under current policy; never bypass current revocation merely because capture claims earlier time. Supervisor can record a separate authorized manual historical attendance correction if evidence/policy permits, with actual supervisor and original capture provenance, not fake accepted historical scan. Keep original capture intent result and observed/server times; no backdating system audit. Reconcile accepted, duplicate, rejected, quarantined, expired, uncertain separately; successful reconciliation applies exactly one authoritative arrival if eligible, others no mutation. Out-of-order/replay across devices, duplicate gates and partial upload must be safe. Upload in bounded batches with per-item outcomes and durable receipts; don't delete queue until authenticated server acknowledgement/explicit reviewed discard (reason, count). Reconciliation idempotent after lost response. No background sync after logout/revoke without authorized device/session review; pending envelopes remain quarantined and can be handed to supervisor through approved recovery. On key rotation/restore, handle unavailable decrypt key as recoverable review/explicit discard, no fabricate success. Retention candidate local pending ciphertext max 24h or configured shorter: on expiry block use, alert and require explicit protected discard or reviewed recovery before purge; document browser OS deletion limits and missing-device procedure. Server records minimal evidence/aggregate on unrecoverable loss, not false attendance. PAC recovery includes queue/key reconciliation but not unrestricted access to plaintext guest data.

### 17.3 Blueprint §13.4 local-validation package (planned extension, separate reviewed security gate)

The later local-validation mode supplements §17.2; it cannot bypass the same bounded lease, encrypted capture, actual actor and authoritative reconciliation. Build server-side a minimal signed/versioned package for exact authorized event/session/station/device/operator and admission scope, with package ID, event/plan/policy revision, generation time, expiry, current eligibility/credential-verifier snapshot, permitted offline actions and minimal fields strictly necessary for local gate feedback. Prefer no guest names or allocation details; if destination fields are operationally necessary, include only reviewed station/session-limited approved labels with explicit stale indication. No contacts, registry, other events, restricted notes, prerequisite/security layers, raw live pass or reusable portal/RSVP credential. Do not expose a global digest list: use a reviewed scope-limited verifier scheme for high-entropy credentials (e.g., keyed per-package verifier, protected key handling and authenticated encryption, with exact scope and expiry); evaluate stolen-package and malicious device threat, do not mistake encryption with an available key for hardware isolation. Server validates scope and current authority on issue/renew; package authenticity/integrity, context, expiry and monotonic time checked locally before use, fail closed on tampering/clock doubt/storage failure. Encryption at rest is required for supported deployment of this mode; unsupported devices use strict/deferred capture as permitted, no plaintext fallback. Store within bounded protected device storage, no public service-worker cache; refresh only online after reviewed auth, invalidate on reconnect/revocation and expire locally, clear package when lease ends/context changes (retain only independently encrypted pending intents for reconciliation).

A scanned token can match a **locally known eligible** verifier, not present in snapshot, locally repeated or invalid/expired under available data. Use explicit text “locally validated — pending server reconciliation” with snapshot age, policy/plan revision and warning of unavailable revocation/duplicate information; never label it server-confirmed, never infer actual physical entry. If separate identity verification is required, follow the approved human procedure; no offline factor bypass. Unknown/locally rejected or outdated package routes to supervisor/help; do not display another guest or auto-enroll. Local duplicate detection is scoped to the device only. Capture uniquely identified intent, original package ID/digest and local outcome as evidence (not authorization); all §17.2 encryption, bounds, receipt, rejection and quarantine rules apply. Reconnect first checks current revocations/lease and refreshes package, then reconciles pending intents via server authority; captured attempts under changed policy/credential/session/assignment must not be silently accepted. Preserve original local outcome and authoritative result; discrepancies are explicit and attributed.
