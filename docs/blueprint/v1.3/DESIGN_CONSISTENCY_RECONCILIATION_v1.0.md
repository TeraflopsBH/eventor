## 1. Precedence and interpretation (apply before affected implementation)

1. Accepted ADRs and approved explicit successor decisions govern their subject; current schema, OpenAPI and runtime define implemented behavior and compatibility. A discrepancy between runtime and design is a gap or defect to assess, not permission to weaken the approved safety requirement. Never silently alter accepted ADRs or old migrations.
2. Blueprint v1.3 Part I is consolidated design; Parts II–V preserve detailed scope, source identities, acceptance and traceability. A detailed approved requirement, exception or safety condition is not erased by summary, historical wording, or an omitted sentence. Read the original clause and this reconciliation alongside relevant current contracts. Later approved domain-specific decisions prevail only on their explicit subject. No blanket “newest document wins”.
3. Apply the more protective nonconflicting invariant; if requirements genuinely conflict, do not invent a permissive or restrictive new business policy. Preserve current authorized behavior, record conflict/impact, obtain reviewed successor decision before changing affected authority, behavior or scope. Do not start unsafe new privileged features merely because current compatibility permits existing actions. Existing independent business roles, tenant isolation and integrity remain protected.
4. Exact original TDS/PAC clauses retained alongside integrated versions. Do not assume all differing text is equivalent or all original-only proposals are binding. The crosswalk identifies both directions; compatible approved requirements and detailed acceptance conditions remain candidates for explicit cumulative confirmation OD-02, no silent deletion. Original source proposals for implementation choice, numeric target, DDL, route name, permission code or legal/tenant policy remain proposals. No precedence rule converts proposals into approved engineering commitments.
5. New work uses actual current checkout, accepted ADRs, current [project state](../../PROJECT_STATE.md), [roadmap](../../ROADMAP.md), [Codex handoff](../../CODEX_HANDOFF.md) and issue status. Historical references and receipts are evidence as of their date; do not re-execute superseded commands or reset branches. Preserve #104/#112 → #105–107 → #110/#111/#108; final integrated Phase 9 only. Review affected engineering decisions at owning M0 or earlier only when necessary to avoid unsafe dependency. No unrelated closure gate or new issue queue.
6. CI and docs-only integrity do not certify implementation or acceptance. Distinguish applicable mandatory requirements, optional tenant activation, optional product extension, explicit owner-approved scope change and test not run. No waiver of critical integrity, isolation or credential security. Never claim skipped external evidence passed.

## 2. Reconciliation ledger

### DC-01 — Platform authority (High; material decision OD-01 remains open)

Sources: [ADR 0015](../../decisions/0015-email-first-login-and-platform-administration.md) lines 13–27; [PAC](../../implementation-design/v0.3/PLATFORM_ADMINISTRATION_CENTER_DESIGN_v1.0.md) §2 critical reconciliation, §§3–5,13,20,21 (AC-03/04/05/07/31/32/35/38); B13-GOV-01/02, B13-SECURITY, decision ledger; ADRs 0010,0017,0020. Managed role reconciliation currently includes non-platform codes; future PAC governance excludes automatic confidential tenant access. Tenant RLS is necessary but not sufficient to separate privileges inside a tenant. This is a design discrepancy, not evidence of an actual exploited vulnerability.

**Compatibility rule:** keep host-only platform flag, actual actor, selected-tenant RLS, membership/session revocation and independent ordinary memberships as accepted. Do not grant new sensitive capabilities automatically by relying on blanket legacy provisioning; if a new code would be inherited, review the affected path before introducing it. No new PAC data access path or privilege expansion under this reconciliation. Audit effective grants (including inherited and indirect roles, read/export/job/stream/template/callback), actual down-stream checks and recovery; record findings without exposing data.

**Proposed successor decision OD-01 (not accepted):** distinguish host authority, explicitly designated platform owner, delegated PAC operator, independently granted tenant business role, time-bounded approved support grant, and exceptional protected recovery. Platform-managed baseline uses an explicitly reviewed low-risk allowlist; new codes default excluded. Sensitive access requires lawful data-owner authority and exact scope/purpose/expiry; strong MFA and step-up, no self-grant/proxy promotion, real actor, audit read/change/export, revocation at command/stream/job/download. Emergency technical containment/recovery without content access where authorization absent; single-owner local protected recovery not blanket data self-approval. Retain ordinary tenant grants and separate account/membership identity; preserve last usable administrator and owner recovery. Propose successor ADR at PAC M0/M1 after populated permission inventory, review actual role catalogue and migration/rollback/lock ordering; do not replace ADR 0015 in docs or code now.

**Evidence required:** existing and new permission inventory, two-tenant negative matrix (all surfaces), populated upgrade preserving independent memberships and removing only approved managed grants, new sensitive code excluded, old sessions and pending work re-evaluated/revoked as policy requires, concurrent grant/revoke/current command, host bootstrap/recovery and ordinary tenant login unaffected. Acceptance PAC-AC-03/04 and remaining PAC controls must not be marked pass until actual evidence.
