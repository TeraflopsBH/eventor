# OpenAPI successor contract design — v0.3

**Status:** proposed API surface and security design; aligned with the canonical OpenAPI v0.3 draft in `docs/api/openapi.v0.3.yaml`  
**Date:** 2026-11-10  
**Depends on:** ADR 0004–0006; accepted MVP/role model; RSVP and Invitation Design v0.3; Cancellation and Event Disruption Design v0.3; Successor PostgreSQL Schema Design v0.3  
**Historical source:** `docs/implementation-design/v0.2/eogp_openapi_v0.2.yaml` (read-only snapshot)  
**Concrete contract draft:** [`docs/api/openapi.v0.3.yaml`](openapi.v0.3.yaml)

## 1. Contract goals

- Preserve the API-first modular-monolith boundary: the API is authoritative for state transitions, permissions, validation, audit and concurrency.
- Keep booking-only venue operations usable without operational event or guest capabilities.
- Represent venue provider, booking customer/requester, contracting party, payer, event organizer and operational task owner independently.
- Make cross-organization access explicit through grant IDs and event-owned snapshot IDs; a booking ID alone never authorizes event or guest access.
- Keep staff session, guest invitation capability, external booking action capability and unauthenticated public intake as separate security contexts.
- Make every state-changing operation idempotent where clients/workers may retry, and concurrency-aware through expected revision / `If-Match`.
- Use purpose-specific request/response schemas. Public/guest projections must never reuse unrestricted staff entities.
- Keep v0.2 OpenAPI unchanged.

## 2. Security schemes and principal types

| Security context | Intended routes | Authority |
|---|---|---|
| Staff session cookie | Staff administration and operational commands | Authenticated user + active organization membership + permission/scope check |
| Guest invitation capability | Guest's own invitation and RSVP actions | One invitation, one guest/event, limited purpose and expiry |
| External booking action capability | External booking requester cancellation/status actions | One booking and allowed external action; no tenant membership |
| Public / no credential | Published booking form and inquiry intake only | Anti-abuse controls; no internal workflow visibility |

Security requirements:
- Public operations explicitly set `security: []`; do not rely on accidental inheritance.
- Guest routes require only the guest capability, never a staff cookie as substitute.
- External booking actions require only the purpose-bound booking capability, never a guest token.
- Staff routes require a staff session plus server-side membership, permission and scope checks.
- Never accept `actorUserId`, `organizationId` or grant identity from a caller as proof of authority. The server resolves actor context; target owner IDs are checked against the authorized aggregate/grant.
- Public capability tokens are opaque, high entropy, stored only as hashes, rate-limited, revocable, purpose-bound and redacted from logs. GET/preview must not mutate or consume a capability.
- Apply CSRF/origin protections to cookie-authenticated mutations; define secure cookie attributes, CORS allow-list, content-type enforcement and request-size limits.
- Return generic not-found/unauthorized outcomes where revealing existence would enable enumeration.

## 3. Common command and response conventions

### 3.1 Headers

- `Idempotency-Key`: required for public submissions and retryable state-changing commands (format and retention window specified in shared header schema).
- `If-Match`: required when mutating a versioned draft, booking, event, grant or configuration revision.
- `ETag`: returned for versioned aggregate representations.
- `X-Request-Id`: generated by server and returned for support/audit correlation; clients cannot use it to impersonate an actor.

### 3.2 Common error model

Use one RFC 9457-style problem response with stable application `code`, safe `detail`, `instance`/request ID and optional field errors. Standard outcomes:
- `400` malformed request; `401` missing/invalid credential; `403` authenticated but not authorized; `404` unavailable/not found; `409` state or reservation conflict; `410` expired/revoked purpose token; `412` stale `If-Match`; `422` domain validation/policy failure; `429` rate limit; `500` generic server failure.
- Conflict responses may include a safe conflict code and current aggregate revision, but never leak another tenant's resource details.
- Disabled optional capability returns a stable `CAPABILITY_DISABLED` response (normally 409 or 404 according to route-discovery policy); do not return success with silently omitted data.

### 3.3 Asynchronous work

Long-running imports, campaign delivery, document rendering and solver runs return `202` plus a scoped job reference. Job status endpoints return only jobs visible to the requesting principal. Outbox/provider delivery is not synchronous with authoritative domain transitions.

Grant acceptance does not grant every member broad access; the actor's membership and role in the grantee organization must also permit the operation. Snapshot routes never mutate provider master geometry.

For `createVenueSnapshotShare`, `approvedLayerIds` must identify spatial layers belonging to the exact `venueSpaceRevisionId`. `approvedResourceIds` may identify resource pools or discrete units belonging to that revision's venue. The database rejects duplicate/foreign identifiers. When the organizer copies the share, each snapshot layer must refer to an approved source layer, every source object must belong to one of those approved layers, and every copied resource must be in the approved resource list. The source revision, its approved layer/object rows and approved resource rows are visible through narrowly filtered RLS only while the share and `venue.snapshot.use` grant remain active. Revocation hides provider master rows from the recipient and blocks new bindings/copies, while the organizer's already-copied event-owned snapshot remains historical data.

### 4.9 Spatial allocation, prerequisites, cockpit and jobs

Keep v0.2 operations where their semantics remain valid, but re-scope them to event-owned snapshots and capability permissions. Add event snapshot provenance to allocation inputs/results. Keep solver output advisory until an authorized human commits it. Check-in routes require the check-in capability. Prerequisite/task routes use explicit responsibility assignment. Cockpit output is permission-projected.

Job operations:
- `GET /jobs/{jobId}` — scoped job status.
- `GET /events/{eventId}/notifications` — permission-filtered notification status.
- `GET /events/{eventId}/audit` — authorized audit projection; never expose token values or unrestricted provider payloads.

## 5. Cancellation and rescheduling command semantics

### Booking cancellation

1. External customer submits a cancellation request using a booking-action capability, or authorized venue staff initiate a venue-side cancellation.
2. Server resolves pinned booking policy and authorized booking contacts.
3. Preview reports policy revision, approval requirement, resource effects and safe commercial consequence summary.
4. Approver decision is a distinct command; rejection/withdrawal leaves confirmed booking and reservations intact.
5. Effective execution locks booking and reservation rows, checks expected revision, applies cancellation once, releases future blocks, retains completed work, records commercial follow-up and writes audit/outbox.
6. Notify booking contacts asynchronously. Linked event receives only a scoped disruption notice.

### Event cancellation

1. Organizer operator requests impact preview and selects reason/internal/public text.
2. Server returns session/guest/invitation/task/booking counts and candidate audience counts without leaking unnecessary guest data.
3. Authorized initiator/approver executes under event revision precondition.
4. Transaction marks event/sessions cancelled, prevents new RSVP/invitation/check-in/credential operations, suppresses pending ordinary messages, preserves history and records campaign/outbox intent.
5. Campaign recipient snapshot is resolved and committed according to selected audience and permissions; actual provider delivery is asynchronous.
6. Linked booking remains unchanged until separately amended/cancelled.

### Postponement

Publish a new schedule revision; never rewrite the old one. A material date/time/venue change may require accepted/tentative guests to reconfirm. Previous responses remain historical answers to the previous schedule. A linked venue booking amendment is a separate request/approval and must secure replacement reservations before releasing the old blocks where feasible.

## 6. Capability and scope behavior

- A venue-only organization can use all Release-1 booking routes without event/guest routes or event rows.
- Event routes require an event-owned record and relevant capability enabled.
- Cross-org routes require both active grant and actor's own organization membership/role.
- Revoked/expired grants prevent new actions immediately; audit and historic snapshots remain.
- External booking contact actions reveal only booking-specific fields and never guest lists.
- Venue provider receives aggregate attendance/capacity only when needed and permitted; no guest identity/RSVP data by default.
- Guest routes reveal only personal invitation/response details and sanitized public event information.

## 7. Contract validation and generation

The final OpenAPI 3.1.1 YAML must include explicit security schemes: `staffSessionCookie` for staff; `guestInvitationCapability` for a guest's own invitation; and `externalBookingActionCapability` for a booking contact's limited action session. Raw bearer secrets are exchanged through a non-mutating POST resolve operation, never placed in query strings, and are redacted from logs. The route inventory must map each command above to concrete operations. The final YAML must:
1. Use globally unique operation IDs and explicit response schemas for every operation.
2. Resolve all local references and path parameters.
3. Define security requirements per route; test the public allow-list.
4. Include examples for success, validation, authorization, stale revision, conflict, expiry and capability-disabled responses.
5. Validate representative payloads with JSON Schema 2020-12/OpenAPI 3.1 semantics.
6. Generate TypeScript types/client artifacts reproducibly from a pinned generator, or use a pinned runtime schema generator; do not hand-maintain duplicate contracts.
7. Add contract tests for booking-only operation, external booking cancellation, venue disruption isolation, RSVP, event cancellation audiences, grant revocation and reservation conflicts.
8. Keep v0.2 YAML unchanged as historical reference.

The contract is subject to the pinned full validator and Redocly lint in CI. Route implementation and request/response contract tests remain separate work; Issue #3 must remain open until those tests are added and pass.
